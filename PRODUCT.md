# XD Guild Command Center

XD / ХД is a Russian-language guild interface for ArcheAge. The existing application provides authenticated member access, role-controlled guild information, member records, activities, attendance and treasury/payroll views. Financial figures and protected actions use the existing application data and permission rules; the visual transfer does not change calculation formulas or transfer gold in the game.

The owner approved redesigning all pages around their supplied near-black/distressed silver XD circular grin seal (2026-11-17). Current visual guidance is in [docs/DESIGN.md](docs/DESIGN.md); the pinned identity and implementation boundary are in [.impeccable/surfaces/silver-identity.md](.impeccable/surfaces/silver-identity.md). This code-led identity supersedes the former orange/purple website reference; the emblem is a brand reference, not an approved UI composition. Local Cormorant Garamond headings and Golos Text interface typography accompany graphite panels, silver financial values and a neutral ivory/charcoal light theme. The owner subsequently approved the third black/scarlet mock and realistic dark-burgundy blood accents on the silver grin seal, shallow upper divider and sparse dried corners. This approved extension is pinned in [.impeccable/surfaces/blood-accent.md](.impeccable/surfaces/blood-accent.md): crimson actions and navigation refine the existing silver world while preserving its layout and all business behavior.

The dashboard supports existing saved panel layouts and a reset control. Its Moscow-time game countdown is an explicit static weekly rotation, separate from real recorded/scheduled activities; it does not create attendance. The user-derived seal assets and provenance live in `apps/web/public/brand/`. Dark/light themes and responsive navigation serve the same real application features, without simulated translations or invented account attributes. The mobile header retains the seal while its navigation drawer is closed.

Temporary pause (2026-11-16): the owner requested hiding the dashboard calculation-period selector, closing reminder, end-date countdown and archive/closing navigation. The archive page and close server action are paused by `PERIOD_CLOSING_ENABLED = false`; historical records, existing attendance/payroll formulas and statistical date filtering are retained for the later redesign. The game-activity countdown remains independent and available.

While periods are paused, attendance defaults to the entire saved activity history on the dashboard, statistics, roster, attendance report and Mini RB purchase candidates. A dedicated authenticated all_time_attendance_report reads source counts and Prime weights with unbounded dates and existing guild/member permissions. Historical accounting partitions are used only to preserve recorded financial obligations; they do not reset attendance. The salary-payment feature replaces monthly preview sums with one lifetime payroll calculation for unallocated sale funds. Already fixed awards and recorded payouts remain unchanged; the roster and payment list share that canonical preview. Unavailable/incomplete history is an error, never a substitute zero. Dashboard RPC reads are partitioned into at most 365-day windows to respect the existing API limit without truncating the lifetime range.

Performance (2026-11-16): dashboard/statistics receive one authorized `command_attendance_data` snapshot with the shared event catalog, permitted member list and present marks. It replaces repeated joined attendance pages and per-row RLS evaluation; classification, totals and date bounds remain unchanged. Snapshot and aggregate reports start concurrently. Financial history reads and lifetime attendance also start concurrently. Auth/role checks still run for every request, without a shared cache or stale payroll data.

While periods are paused, treasury cards and dashboard cash balances use `treasury_lifetime_summary`, which delegates to the established lifetime cash/obligation calculation. Historical sale dates and accounting periods remain unchanged. Balances still subtract recorded payouts and guild expenses; sold revenue and unsold inventory remain separate. The period-scoped RPC is retained for accounting workflows and future period redesign.

The Payments navigation item opens `/payments` directly for active members. It renders the existing RLS-protected settlement panel without requiring treasury.read or redirecting through the treasury inventory page. Pagination remains on the payments route; write actions retain their existing treasury.pay/treasury.spend checks and invalidate both views after changes.

Salary payment workflow: staff with both treasury.pay and treasury.allocate open Payments → «Выплата ЗП». The canonical lifetime payroll report is shared with the roster. Only active members meeting the exact common 20% attendance threshold appear. Prime and Mini RB have independent payout controls and ledger-derived paid indicators; zero accrual is not marked paid. A payment locks the finance transaction, verifies the preview signature, freezes current free-sale shares using the existing exact allocation algorithm and pays only the selected member/source through existing award/payout records. Retries are idempotent, stale previews and ineligible targets are rejected, and failures roll back the entire operation. New sales can create top-ups without rewriting previously paid amounts. Green checks persist through reload and disappear when that source has an outstanding top-up or a payment is reversed. Only user-submitted payment actions record payouts; deployment and production validation perform no real payouts.

Архив активностей независим от финансовых периодов: `/events/archive` позволяет пользователю с `periods.close` и `events.manage` выбрать даты UTC включительно, увидеть количество и подтвердить перенос. Повтор запроса безопасен; архив не запускается при деплое. Текущий журнал, посещаемость, дашборд, статистика, кандидаты Мини РБ и новый расчёт зарплаты исключают архивные события. При частичном архиве остаются другие события; при полном — посещаемость обнуляется до новых активностей. Архивный журнал сохраняет карточки, составы и изображения, запрещая исправления состава/события; снимок посещаемости выбранного диапазона хранится без прямого доступа через клиентский API. Казна, продажи, инвентарь, зафиксированные начисления и выплаты сохраняются; перенос не означает выплату или финансовое закрытие.
