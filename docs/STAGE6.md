# Этап 6A — бот, события и уведомления

Добавлены `/account/telegram`, `/admin/telegram`, `/api/telegram/webhook`, `/api/telegram/dispatch`; миграция 009 применяется после 001–008. Существующие миграции и Express-runtime сохранены. Новых npm-зависимостей нет.

## Реализовано

Двухсторонняя привязка к существующему активному членству с одноразовым токеном (в БД SHA-256), подтверждением Telegram ID на сайте, сроком 10 минут и защитой от чужих/повторных привязок. Username не определяет аккаунт. Подписка включается отдельно. Отвязка не удаляет способ входа Supabase; выход из сессий сайта не отключает бот, для этого есть отдельная отвязка.

`/events` выдаёт пять ближайших будущих событий, `/cabinet` — обычную ссылку на кабинет; `/stop`, `/unlink`, `/help` управляют ботом. Группы/каналы/боты игнорируются. Сайт и бот используют ту же базу событий и финансов. Новые события и изменения расписания, начисления прайма и отмены начислений ставятся в очередь в исходной транзакции. Деньги форматируются точно; уведомление о начислении не называется выплатой.

Webhook сравнивает секрет в постоянном по содержимому времени, ограничивает тело 64 KiB, принимает свежие команды только из личного чата совпадающего отправителя, защищается от повторного update_id и ограничивает команды по Telegram ID. Сервисные RPC недоступны браузерным ролям; внутренние таблицы закрыты и имеют RLS. Перед выдачей задания проверяются актуальная привязка, статус участника, блокировка, подписка и принадлежность начисления.

Очередь использует одно одновременное задание с lease на 2 минуты, fencing token, ограничение частоты, до пяти попыток и retry_after. После действий сайта запускается ограниченный after()-обработчик; при сбое задания остаются в PostgreSQL. Есть ручной повтор и выключенный по умолчанию GitHub Actions-планировщик. Настройка через [TELEGRAM.md](TELEGRAM.md).

Администратор подключает webhook с проверкой имени бота и защитой чужого адреса. Существующие updates не сбрасываются. Секреты не передаются клиенту и не вводятся в формы сайта.

## Влияние на существующие модули

События и начисления получили транзакционные триггеры; их исходные правила и финансовые операции не переписаны. Ошибка внешнего Telegram не откатывает уже сохранённую активность или начисление. Без настроенного бота приложение не вызывает внешнюю доставку. Привязки отсутствуют до ручного подключения; историческая массовая рассылка не создаётся. Прокси не выполняет cookie-auth для защищённых секретами bot endpoints. UI добавляет ссылки на настройки, отдельные согласия и уточнение обработки данных.

## Ограничения и приёмка

Реальный бот/секреты, Supabase/PostgREST/Auth, публичный webhook и планировщик требуют настройки пользователя. Локальные проверки используют тестовую auth-схему и подставные ответы HTTP; реальные сообщения не отправлялись. После развертывания пройти сценарий двух аккаунтов в TELEGRAM.md.

Bot API не поддерживает идемпотентность sendMessage: при потере ответа возможно повторное сообщение. Уже отправляемое сообщение не гарантированно отзывается при отвязке. Без планировщика остаток очереди и отложенные попытки требуют нового действия/ручного запуска. GitHub schedule может задерживаться и пока не активирован. Гарантия доставки в конкретную минуту не даётся.

Привязка/отвязка способа входа OIDC, запись на активности, уведомления о выплатах и Mini App не входят в эту часть. Правило распределения мини РБ осталось прежним. Очистка служебной истории выполняется при новых командах; полноценное удаление аккаунта и согласование контакта владельца ещё нужны.

## Результат проверки

- 86 результатов тестов, TypeScript и production-сборка прошли. Проверяются подтверждение владения, чужие/повторные/истёкшие ссылки, доступ к service RPC, opt-in, транзакционный откат очереди, fencing, предел повторов, принадлежность начислений, отмена и блокировка.
- На отдельном PostgreSQL 17 прошли 12 конкурентных сценариев: девять прежних финансовых и три новых (повтор Telegram update, два отправляющих процесса, попытка привязать один Telegram ID к двум участникам). Контейнер одноразовый, без внешней сети и пользовательских данных.
- `scripts/check-telegram-http.py` проверяет настоящие Next HTTP-обработчики с локальной заменой Supabase: секрет, размер тела, запрет групп, хеш вместо токена в RPC, after(), bearer-доступ к очереди, HTTP 503 при сбое БД. Внешние fetch-запросы заблокированы тестом. Проверка добавлена в CI после сборки.
- Chromium: 24 комбинации (320/390/768/1440 px × шесть состояний). Переполнений, ошибок JavaScript и неподписанных полей нет; согласие на уведомления изначально выключено. Закрытый UI использует явно подписанные вымышленные данные, формы не подключены.
- YAML расписания и вложенный Python проверены; реальный запуск GitHub-планировщика без пользовательских настроек не выполнялся.

В ходе проверки исправлен конфликт имени SQL-переменной и алиаса в выдаче очереди. Тесты дополнены моделированием прошедшего времени для ограничения частоты; исправлен запрещённый для fetch порт локального HTTP-стенда. Итоговые проверки прошли. Действующий Telegram, Supabase Auth/PostgREST и публичный деплой этой проверкой не подтверждены.
