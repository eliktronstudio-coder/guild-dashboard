# Этап 1 — основа, 2026-10-31

Статус: код первого модуля реализован и проверен локально; облачное подключение и приёмка ещё впереди. Это не объявление полного завершения этапа 1.

## Реализовано

- Отдельное приложение `apps/web`: Next 16.4.3, React 19.3.1, Supabase JS 2.118.0 / SSR 0.12.7, Tailwind 4.3.3, TypeScript; lockfile, Node 24, CI-конфигурация.
- Сохранены B0, S1, F1. Временная монограмма XD, локальные лицензированные шрифты WOFF2, оптимизированный фон WebP, мобильное меню, короткое появление контента, focus/reduced-motion. Полный дизайн и эмблема отложены владельцем.
- Telegram custom OIDC / PKCE через Supabase, email/password, callback и token-hash подтверждение, восстановление после подключения SMTP. Способы входа включаются явно; без конфигурации успех не имитируется.
- Обязательный ник и два согласия с версией; pending, одобрение/отказ, причина отказа, защита повтора. Заявка не резервирует ник; уникальность проверяется при приёме в транзакции. При совпадении ника пользователи никогда не объединяются.
- PostgreSQL-миграция: профили, заявки, членство, шесть ролей, отдельные permission keys, выдача ролей, блокировка, аудит. Владельца назначает закрытый bootstrap по проверенному auth UUID.
- Серверная авторизация и RLS. Клиент не пишет таблицы напрямую. Старые JWT проверяются по текущему членству/правам, auth.sessions и списку отзыва; изменение роли действует сразу. Блокировка отзывает сессии, разблокировка их не восстанавливает.
- Состав с поиском и пагинацией, счётчики реальных членств/заявок, кабинет, администрирование заявок, блокировки и назначение ролей владельцем, последние 20 действий.
- Документы и пошаговое подключение с телефона. Старые `server.js`, `src/`, `public/`, корневой package.json не изменены.

## Проверки и границы доказательств

Пользовательский сценарий: вход → серверная сессия → обязательный ник → SQL-функция заявки → администратор → транзакция приёма → RLS допускает участника.

| Граница | Проверено | Ограничение |
|---|---|---|
| TypeScript и production-сборка | `npm run check`: успешно | Не подтверждает облачный деплой |
| Нормализация и callback-переходы | 3 unit-теста | Разрешённый алфавит временный, сервер ArcheAge ещё неизвестен |
| PostgreSQL/RLS | 7 вложенных сценариев + родительский тест; реальные SQL-функции в PGlite | Таблицы Supabase Auth и JWT claims — тестовые fixtures; не реальная OAuth-сессия |
| Анонимный/участник/офицер/владелец | Запрет прямой записи и повышения прав, self-review, чужая область; смена роли | Конкурентные соединения настоящего Supabase ещё не проверены |
| Конфликт ников и повтор решения | Кириллица/регистр/пробелы/похожие буквы, повтор RPC, откат при конфликте | Без реальных игроков |
| Блокировка и выход | Отзыв текущих JWT по session_id; unverified и удалённая сессия закрыты | Реальная цепочка refresh token проверяется после подключения |
| Публичный UI | Chromium, 320/390/768/1440 px: 24 страницы, 0 JS-ошибок, 0 переполнений | Не физические телефоны, не Safari |
| Закрытые маршруты без настроек | 24 проверки редиректа на `/setup` | Защищённые экраны с реальным Supabase ещё не пройдены end-to-end |
| GitHub CI / Vercel / SMTP / OIDC | Конфигурация и инструкции подготовлены | Фактический результат отмечается отдельно после запуска |

При разработке тест нашёл неоднозначную SQL-ссылку на параметр `reason`; исправлена. После исправления локальные проверки проходят. Все приватные страницы принудительно динамические; авторизованные ответы не кэшируются как общедоступные.

## Что остаётся

Подключить новый Supabase, применить миграцию, настроить Telegram, закрыто назначить владельца, провести реальный сценарий двумя аккаунтами, первый отдельный деплой, проверка backup/restore и телефона. SMTP при отсутствии выключен. Принять тексты правил/данных и контакт владельца до приглашения участников.

Привязка/отвязка Telegram, история ника, персонажи, редактирование матрицы разрешений, настройки бренда, полный аудит/экспорт и резервирование ещё не реализованы. Поэтому BR-01, ID-05 и этап 1 целиком не помечены выполненными. Статистика событий/финансов и бот-уведомления относятся к следующим этапам. Времена в текущих экранах явно UTC; часовой пояс гильдии предстоит выбрать.
