# Этап 4 — казна прайма, мини РБ, гильдии и имущество

Обновлено 2026-11-01. Реализован первый финансовый модуль в одной вкладке `/treasury`. Код готов к подключению тестового Supabase; облачный деплой и настоящий вход пока не проверены.

## Правила владельца

| Итог | Расчёт |
|---|---|
| Казна прайм | 70% полученной выручки от прайм-дропа |
| Казна мини РБ | 100% полученной выручки от дропа мини РБ |
| Казна гильдии | 30% полученной выручки только от прайм-дропа |
| Общая казна | Оценочная стоимость оставшегося дропа в обоих инвентарях |

Пользователь явно уточнил пример: прайм-продажа на 100 000 → 70 000 в прайм, 30 000 гильдии. Для мини РБ удержания гильдии нет. Карточка прайма дополнительно показывает полную выручку. Общая казна — имущество, она не прибавляется к сумме золота как ещё один денежный баланс.

**Общий инвентарь** содержит только прайм-дроп. **Инвентарь ХД** — только дроп мини РБ. Направление определяется на сервере по пометке активности, а не по выбранной в браузере вкладке.

Оценка непроданного имущества принята как рабочее допущение: остаток × оценочная цена единицы. Пользователь отдельно не уточнил метод оценки. Цена может отсутствовать: такая партия видима, а общий итог помечен как неполный; при отсутствии всех оценок показано «Нет оценки».

## Сценарий работы

1. Создать активность и на её странице назначить пометку «Прайм» или «Мини РБ». Это могут делать пользователи с `events.manage` или `treasury.manage`. Указать основание. Название/тип активности не заменяют пометку.
2. Завершить активность. В разделе «Казна» выбрать месяц и эту активность; внести название, категорию, количество и при наличии оценочную цену. Дроп поступает в нужный инвентарь автоматически. Переноса данных из игры нет — фактический дроп вводится вручную.
3. В партии открыть «Записать продажу», указать проданное количество и **общую полученную сумму этой продажи**, не цену единицы. Предварительное распределение видно до подтверждения; окончательный расчёт выполняется сервером.
4. После сохранения остаток уменьшается, соответствующие денежные казны растут. Непроданный остаток продолжает входить в оценку имущества. Частичные продажи поддерживаются.
5. Ошибочную продажу отменить с причиной и подтверждением: все первоначальные поступления снимаются, предметы возвращаются. Запись остаётся в истории; повтор отмены не возвращает товар второй раз.
6. Название, категорию, общее количество, заметку и оценку партии можно исправить с причиной. Уже проданное количество уменьшить нельзя. Чтобы убрать ошибочную непроданную партию из наличия, поставить общее количество 0; история сохраняется.

После первой партии пометка активности фиксируется: нельзя перенести уже учтённый прайм в мини РБ. Ошибочный источник потребует отдельной контролируемой операции переноса в будущей версии; ручное редактирование таблиц не является пользовательским сценарием.

## Точность, права и история

- Все деньги хранятся в целых единицах по 0,0001 золота. SQL использует bigint/numeric, клиент — BigInt; денежные поля API возвращаются строками. Расчётов через `float`/`Number` нет.
- Рабочее правило округления: 30% каждой продажи округляются вниз до 0,0001, весь остаток сохраняется в прайме. Для целого примера 100 000 получаются ровно 70 000 и 30 000. Сумма долей всегда равна выручке. Это техническое правило минимальной единицы, а не отдельно утверждённый владельцем игровой регламент.
- Количество — целое, до 1 000 000 в партии. Предел цены единицы/суммы одной продажи — 10 000 000 000 золота. Общая оценка может быть больше предела одной операции и передаётся без потери точности.
- `treasury.read`: owner/admin/officer/treasurer/member. `treasury.manage`: owner/admin/treasurer. Офицер может назначить пометку, но не распоряжается казной без соответствующего разрешения.
- Проверки origin/сессии/прав на сервере, повторная авторизация в SQL, RLS, закрытые прямые записи. Создание партии и продажи имеет UUID запроса; версия партии предотвращает перезапись устаревшей формы.
- Все изменения выполняются транзакционно с общим порядком блокировок: гильдия → объект. После ожидания блокировки проверка прав повторяется. Создание/правки/продажи/отмена сохраняются в журнале с автором; отменённые продажи остаются видны в «Казне».
- Суммы агрегируются в PostgreSQL по всем активным продажам и остаткам. Пагинация UI не обрезает итоги. Инвентарь — по 20 записей, продажи — по 10, выбор завершённых активностей — по 50 с фильтром месяца.

## Проверки

- 56 автоматических результатов тестов: миграции, права, RLS, изоляция гильдий, запрет прямых записей, пример 100 000 → 70 000 + 30 000, мини РБ без отчисления, повторные запросы, частичная продажа, недостаток товара, устаревшие формы, откат ошибочной операции, отмена, переоценка, история и значения больше безопасного диапазона JavaScript Number.
- Production-сборка Next.js и TypeScript проходят.
- В Chromium проверены оба инвентаря и режим участника на 320/390/768/1440 px: без переполнений, ошибок JavaScript и полей без подписей. Проверен настоящий клиентский компонент предварительного распределения: 100 000 → 70 000 + 30 000, мини РБ 100%, дробные суммы. Для просмотра использовались явно подписанные вымышленные данные, без рабочих серверных форм. Закрытый маршрут `/treasury` без Supabase направляет на `/setup`.
- Дополнительно проверены пять сценариев в **PostgreSQL 17 с отдельными соединениями**: конкурирующие продажи последнего предмета, одинаковые запросы, одновременная отмена, смена пометки во время добавления первой партии и отзыв прав у ожидающей операции. Все прошли.
- Воспроизведение SQL-конкурентности: `cd apps/web && python scripts/check-treasury-postgres.py`. Нужны локальный Docker и образ `postgres:17-bookworm`. Скрипт создаёт временный контейнер без сети/публичных портов, использует вымышленные auth-данные и удаляет контейнер в конце. Это не настоящий Supabase/OIDC.

## Подключение и границы

Применить `202610310006_treasury.sql` **после 001–005**; опубликованные миграции 001–005 не менялись. Существующие активности получают «Без пометки», поэтому ничего не классифицируется по названию задним числом. Существующие участники, персонажи и посещаемость сохраняются. [Инструкция для владельца](SETUP.md).

Денежные карточки сейчас отражают накопленные поступления за вычетом отмен. Расходы, начальные остатки, комиссии торговли, распределение прайма между конкретными игроками, выплаты и обязательства ещё не реализованы. Следующая часть этапа 4 потребует правил получателей и выплат. Зачисление 70% в казну прайма **не означает выплату игрокам**.

До приглашения пользователей нужна приёмка реального Supabase/PostgREST двумя аккаунтами, проверка RLS с настоящими JWT, мобильных устройств и backup/restore. Перенос финансов старого Express-приложения не выполнялся.
