# Проверяемый выпуск XD на Timeweb

Новый workflow `XD verified release` выполняет типизацию, тесты, production build, HTTP-проверки и PostgreSQL backup/restore на синтетических данных. Только успешный запуск для `codex/xd-foundation-20261031` получает production SSH secret и передаёт серверу проверенный SHA. PR не получает доступ к серверу. Обычный push в ветку разработки ничего не устанавливает.

Сервер сверяет SHA с текущей опубликованной веткой, блокирует параллельные запуски, создаёт зашифрованную копию вне сервера перед ожидающими миграциями, применяет миграции и запускает существующий сборщик релиза. Ошибка резервирования блокирует изменение БД. SHA считается установленным только после проверки запуска приложения. Откат service не откатывает БД; будущие миграции должны быть совместимы с предыдущим приложением. `/login` проверяет HTTP-доступность, но не подтверждает вход реального пользователя.

## Однократное подключение

Хранилище пользователем пока не выбрано. Внешняя загрузка и рабочее резервирование остаются выключены.

Эти изменения подготовлены для PR; рабочая Supabase, сервер и расписание пока не изменены. GitHub connector не позволяет проверять наличие repository secrets. Наличие ключа подтверждено пользователем, реальный SSH ещё не проверен.

1. Добавить `TIMEWEB_SSH_KNOWN_HOSTS` в GitHub Actions secrets: запись для `200.165.236.194`, проверенная по fingerprint через консоль Timeweb. Не доверять результату ssh-keyscan без независимой сверки. `TIMEWEB_SSH_PRIVATE_KEY` уже добавлен пользователем. В GitHub environment `production` при необходимости ограничить разрешённую ветку.
2. На VPS остановить старый опрос **до слияния PR**, чтобы старый скрипт не установил непроверенную версию:

```bash
systemctl disable --now xd-guild-deploy.timer
systemctl stop xd-guild-deploy.service
```

3. Установить совместимые с сервером PostgreSQL клиенты `psql`, `pg_dump`, `pg_restore`, GnuPG и публичный ключ получателя копий. Приватный ключ расшифровки хранить отдельно от VPS. Настроить root-owned libpq service/passfile, TLS CA и `sslmode=verify-full` для прямого или session-pooler подключения Supabase; transaction-pooler не использовать.
4. Создать `/etc/xd-guild/deploy.env` с владельцем root и правами 600. Значения вводить только на сервере, не в чат:

```ini
PGSERVICE=xd-production
PGSERVICEFILE=/root/.pg_service.conf
PGPASSFILE=/root/.pgpass
PGSSLMODE=verify-full
XD_BACKUP_DIR=/var/lib/xd-guild-backups
XD_BACKUP_RECIPIENT=FINGERPRINT_ПУБЛИЧНОГО_GPG_КЛЮЧА
XD_BACKUP_UPLOAD=/usr/local/sbin/xd-upload-backup
```

Файл совместим с Bash `source` и systemd EnvironmentFile: использовать простые абсолютные пути без shell-подстановок. `xd-upload-backup` — отдельный root-owned исполняемый файл, принимающий два пути: зашифрованный дамп и JSON-манифест. Он должен загрузить оба в защищённое хранилище вне VPS, сверить удалённую SHA-256 и завершаться ненулевым кодом при ошибке. До его настройки выпуск блокируется. Автоматическое удаление копий не включено; срок хранения и контроль свободного места настроить в выбранном хранилище.

Готовый S3-загрузчик поставляется в `scripts/upload-backup-s3.py`. После выбора провайдера установить AWS CLI v2 и настроить профиль на VPS (ключи вводятся в защищённый профиль, не в GitHub/чат). Ограничить доступ нужным бакетом: загрузка и чтение объектов; удаление не требуется. Для Timeweb или другого S3 задать endpoint выбранного провайдера через `AWS_ENDPOINT_URL`. Установить загрузчик:

```bash
install -o root -g root -m 700 scripts/upload-backup-s3.py /usr/local/sbin/xd-upload-backup
```

Добавить в `deploy.env`:

```ini
AWS_PROFILE=xd-backups
AWS_DEFAULT_REGION=РЕГИОН_ПРОВАЙДЕРА
AWS_ENDPOINT_URL=https://ENDPOINT_ПРОВАЙДЕРА
XD_BACKUP_S3_URI=s3://ИМЯ_БАКЕТА/xd-guild
```

Загрузчик скачивает оба объекта обратно и сравнивает SHA-256; успешный PUT сам по себе не считается проверкой. Это требует дополнительного исходящего трафика. Бакет не должен иметь публичного доступа. Выбор/покупка бакета и политика хранения ещё не выполнены.

5. После успешных CI-проверок и слияния получить новый код на VPS при остановленном старом таймере:

```bash
cd /var/www/xd-guild-command-center
git pull --ff-only origin codex/xd-foundation-20261031
```

6. По журналу Supabase и фактической структуре независимо проверить последнюю уже применённую миграцию. Не считать наличие одного объекта доказательством всех миграций. Затем записать исходную историю с **точным именем проверенного файла** (не подставлять 018 по умолчанию):

```bash
set -a
source /etc/xd-guild/deploy.env
set +a
python3 scripts/database-release.py baseline --through ИМЯ_ПРОВЕРЕННОГО_ФАЙЛА.sql
```

Baseline сначала создаёт и загружает копию, затем записывает контрольные суммы, без повторного выполнения SQL. При отсутствии исходной истории автоматические миграции отказываются запускаться. Изменение или удаление применённого SQL также блокирует выпуск. Новая миграция и её запись в истории фиксируются одной транзакцией.

7. Выполнить `bash scripts/install-database-backup-timeweb.sh`. Установщик сначала проверяет настоящую копию, затем включает ежедневный backup около 01:00–01:15 UTC (06:00–06:15 Екатеринбург). Настроить мониторинг ошибок systemd и хранилища. Затем перезапустить workflow `XD verified release` для актуального коммита опубликованной ветки.

Проверка: `systemctl status xd-guild-backup.timer`; `journalctl -u xd-guild-backup -n 30 --no-pager`; GitHub Actions → XD verified release. Старый install-auto-deploy-timeweb.sh больше не нужен: вызов нового auto-deploy-timeweb.sh без SHA ничего не устанавливает.

## Границы копии

pg_dump читает всю доступную подключённой роли базу без исключения схем и останавливается при ошибках прав. Он не копирует файлы Storage, внешние роли кластера, настройки Auth/OAuth, webhook и серверные секреты. Доступность всех требуемых объектов для выбранной роли проверить при живой приёмке. Проверка каталога и SHA не заменяют восстановление. До признания резервирования рабочим выполнить восстановление в отдельный тестовый проект по `docs/BACKUP.md`. На рабочую Supabase восстановление автоматически не запускается.
