# Справочники и коэффициенты — 2026-11-03

## Использование

Администратор и владелец: Управление → Список дропа / Рейд-боссы. Добавление, редактирование и архив; уникальное активное название внутри каждого справочника. Фото выбирается с устройства (до 10 МБ), обрезается по центру до 100×100 и показывается 50×50. PNG-миниатюра хранится в БД; отдельный Storage не нужен. Цена предмета справочная, не заменяет фактическую сумму продажи и пока не подставляется в партии автоматически.

Состав: коэффициент каждого игрока 0,20–1,25, шаг 0,01. Все существующие и новые участники получают 1. Изменение — только администратор/владелец, с проверкой версии и записью в аудит.

Рейд-босс: вес 0,01–1000 (технический диапазон), по умолчанию 1. В карточке события выберите РБ; имя и вес сохраняются в событии. Правка справочника не меняет уже сохранённый вес события. Коэффициенты игрока берутся на момент нового расчёта и затем фиксируются.

Казна → Распределить фонд по РБ: выбрать месяц UTC и до 100 завершённых событий Прайм с РБ и подтверждённой явкой. В фонд входят все ещё не распределённые продажи этих событий (70% игрокам; 30% гильдии не меняются). Выбранное событие без продаж тоже даёт баллы за явку. Мини РБ и его отдельная казна остаются вне распределения, как в прежних правилах.

Баллы игрока = его коэффициент × сумма весов выбранных РБ, где стоит «Присутствовал». Сумма игроку = фонд × баллы / общие баллы. Округление до 0,0001 золота по наибольшим остаткам; равные остатки — по стабильному ID. Общий фонд полностью сохраняется. Внутренне суммы привязаны к исходным продажам, поэтому один игрок может получить несколько строк начислений; итог совпадает с предварительным расчётом. Расчёт не отправляет золото в игре.

Предпросмотр проверяется повторно под блокировкой гильдии. Изменения явки, коэффициентов, продаж или названий требуют нового просмотра. Повторный запрос не дублируется. История хранит снимок событий, получателей, весов и сумм. Старые начисления не пересчитываются. Обычные события без РБ распределяются по коэффициентам участников в прежнем экране отдельной продажи.

Отмена любой строки общего фонда отменяет весь фонд, только если нет действующих выплат. Исправление явки после начисления блокирует выплаты по этому фонду до восстановления явки либо отмены расчёта. Изменения коэффициентов после начисления не меняют старые долги и не блокируют выплаты.

## Установка на Timeweb

1. Сделать резервную копию рабочей Supabase по docs/BACKUP.md.
2. В Supabase SQL Editor выполнить последовательно `apps/web/supabase/migrations/202611030017_catalogs.sql` и `202611030018_weighted_pools.sql` поверх 001–016. Оба файла — добавочные миграции. Старый RPC `allocate_treasury_sale` после 018 намеренно требует обновить расчёт; до обновления приложения новые начисления недоступны.
3. На сервере из исходного checkout:

```bash
cd /var/www/xd-guild-command-center
git pull --ff-only origin codex/xd-foundation-20261031
bash scripts/deploy-timeweb.sh
```

Скрипт предварительно проверяет новые таблицы через Supabase, собирает отдельный каталог релиза, оставляет действующее приложение работающим во время сборки, затем переключает systemd. При неуспешном старте возвращает предыдущий service. Секреты не выводятся, .env остаётся 600. Прежнее приложение на 3000 и nginx не меняются. Автоматический возврат service не откатывает миграции; они добавочные, но старый интерфейс начислений после 018 требует обновления. Скрипт проверен синтаксически, на VPS из среды агента не запускался.

4. Ctrl+Shift+R в браузере, проверить вкладки, фото, изменение коэффициента, выбор РБ в событии. Первое реальное начисление подтверждать только после проверки присутствовавших и сумм.
