# Этап 2 — профили и персонажи

2026-10-31. Реализован самостоятельный модуль поверх основы. Владелец параллельно подключает Supabase; реальная авторизация и облачный end-to-end ещё не подтверждены. Дизайн остаётся отложенным.

## Поведение

- У каждого участника стабильная страница `/members/<membership UUID>`. Смена ника не меняет адрес, аккаунт, персонажей или роль.
- Профиль показывает ник, роль, дату вступления, описание, аватар с инициалом и выбираемым цветом, основного и дополнительных персонажей.
- У персонажа имя, сервер, класс и специализация. Пока сервер/версия ArcheAge не уточнены, последние поля — свободный текст, без выдуманного фиксированного справочника.
- До 20 активных персонажей на участника. Первый становится основным. Выбор нового основного атомарно снимает этот признак с прежнего. Устаревшая форма не перезаписывает более новое изменение.
- Архивирование сохраняет запись. Если архивируется основной персонаж, основным становится первый оставшийся по времени создания и UUID. Если персонажей нет, основного нет. Архив виден владельцу профиля и уполномоченной администрации, показываются последние 20 записей.
- Смена ника требует причины и подтверждения, проверяет активную уникальность и похожие символы, сохраняет старый/новый ник, автора и время. Повтор запроса с уже установленным ником ничего не дублирует. Самостоятельные изменения ограничены одним в минуту; администратор может исправить ошибку.
- Старый ник освобождается, но никогда не связывает другого пользователя с прежним аккаунтом. Это явно указано в форме. Персонаж и отображаемый ник участника меняются отдельно.
- История ников с пагинацией видна самому участнику и администрации. Email и Telegram ID в публичном для гильдии профиле не выводятся.
- Состав: поиск по нику, фильтры роли/класса основного персонажа/сервера, сортировка по нику или дате вступления, 25 участников на странице. На телефоне вместо широкой таблицы — карточки.
- Управление блокировкой и ролями перенесено со строки списка на профиль. Старые возможности сохранены.

## Права и база

Аддитивная миграция [202610310002_members.sql](../apps/web/supabase/migrations/202610310002_members.sql). Первую опубликованную миграцию не меняли. Новые таблицы `characters`, `nickname_history`; поля профиля в `memberships`; invoker-view `member_directory` сохраняет RLS при поиске и пагинации.

Свой активный профиль редактирует сам участник. Другой профиль — пользователь с `members.manage`; офицер по умолчанию этого права не имеет. Профиль владельца нельзя редактировать чужим аккаунтом. Операции проверяются на сервере и повторно в SQL под блокировкой; обычные роли не имеют прямой записи в таблицы. `guild_id` и составные FK защищают связи между гильдиями. Изменения профиля, персонажей и ника пишутся в аудит в той же транзакции.

Коллизии имён персонажей проверяются внутри одного участника и одного сервера; имя персонажа не является доказательством владения игровым аккаунтом. Проверки фактического владения через ArcheAge API нет.

## Проверки

- `npm test`: 28 результатов, все проходят. Включены регрессии первой миграции, обновление существующих членств без смены UUID/дат/ролей, self/admin/officer/pending/blocked, чтение через invoker-view, чужая гильдия, прямые записи, конкурентно устаревшие версии, повтор создания/архива/ника, единственный основной персонаж и архивирование последнего.
- TypeScript и production-сборка Next.js проходят.
- Проверены фильтры с повторяющимися URL-параметрами, сохранение фильтров при пагинации, буквальный поиск `%`/`_` и экранирование пользовательского текста при HTML-рендере.
- Chromium: компонент состава проверен на 320/390/768/1440 px; корректное переключение таблицы/карточек, переполнений и ошибок JavaScript нет. В production-сборке проверены 5 закрытых маршрутов (включая новый профиль): без конфигурации направляют на подготовку.
- При проверке форм учтена перерисовка после смены версии записи: поля сбрасываются вместе с версией, сообщение результата сохраняется; устаревший текст не получает молча новую версию.
- Для браузерной проверки компонента состава используется изолированный fixture `scripts/review-member-ui.tsx`, с явной пометкой вымышленных участников. В production нет демонстрационного входа или обхода авторизации. Это проверка компонента, не работающей Supabase-сессии.

SQL выполнялся в PGlite: PostgreSQL-функции и RLS настоящие, Supabase Auth и JWT claims — тестовые fixtures. Параллельные подключения настоящего PostgreSQL и облачные операции ещё требуют проверки. Тесты устаревших версий не объявляются нагрузочным тестом.
